## 生成图

- 节点：`load_confirmed_spec`（取冻结 `SpecVersion` 并校验 `content_hash==hash`，编译契约）→ `resolve_assets`（M14 解析资产锁）→ `assemble`（M15 写入 run 目录）→ `verify`（调用 Runner `/verify` + `/accept`）→ `package_or_fail`。
- 状态机与数据库权威：`QUEUED→PLANNING→GENERATING→VERIFYING→SUCCEEDED/FAILED`；每节点写 `task`/`event`；`assemble` 记 artifact（manifest hash）。**仅当 4 项构建检查全 `PASS` 且 `/accept` `overall=PASS` 才 `SUCCEEDED`**，否则 `FAILED`（含 `INFRASTRUCTURE` / `VERIFICATION_FAILED`）。
- 异常兜底：`run_generation` 捕获未预期失败 → 落 `FAILED` + `failed` 事件（不伪造成功）。
- 仅接收已确认规格：未确认（`confirmed_at` 为空）→ `FAILED/SPEC_NOT_FOUND`；hash 不符 → `SPEC_CONFLICT`。

## worker 集成

`worker.run_worker` 领取（租约）后调用处理函数，**默认即生成图**（`Runner` 地址/密钥/工作根来自环境 `RUNNER_BASE_URL`/`RUNNER_TOKEN`/`RUNNER_WORK_ROOT`）；等待用单调时钟。handler 签名由 `(Session,Run)` 改为 `(run_id)`，避免与领取事务嵌套。

## 修复的真实缺陷（M23 E2E 暴露）

`runner/acceptance.py` 的 `delete_own` 期望值用 `_ADMIN[0]`（**用户名 `admin`**）去和契约的**角色**比较，恒判“无删除权”→ 期望 403 而实际 200 → 误报失败，并导致生成图误判 `VERIFICATION_FAILED`。修正为使用角色常量 `_ADMIN_ROLE="ADMIN"`。此为 M18 验收的既有缺陷，由本步真实 E2E 发现并修复。

## 验证（实测）

1. 平台 `uv run --locked pytest` → **178 passed**（含 M23 5 例）；`runner` 测试通过；两者 `ruff` 全绿。
2. **真实端到端（Docker + 真实 Runner）**：确认 Task 规格 + QUEUED run → `run_generation` → 真实装配 + Runner `/verify`(全 PASS) + `/accept`(全 PASS，含 MySQL digest 对账) → **`SUCCEEDED`**；tasks=`{load_confirmed_spec,resolve_assets,assemble,verify}`；events=`claimed→stage×3→verification→succeeded`；无残留容器。
3. **真实失败分支**：Runner 依赖离线（`network=none`）→ 图 → **`FAILED/INFRASTRUCTURE`** + `failed` 事件。
4. 集成测试：`test_generation_graph.py`（成功/`FAIL`/`INFRASTRUCTURE`/未确认规格/缺必需项不成功）。真实模板/编译错误的 `FAIL/BUILD_FAILED` 检测由 M17 Runner 覆盖，图将任何 verify `FAIL` 统一落 `FAILED` + 事件。

## 剩余风险 / 阻塞

- `verify` 通过 HTTP 调 Runner，需 **worker 与 Runner 共享工件根**（`RUNNER_WORK_ROOT`），MVP 单机成立。
- 单 worker、串行；崩溃接管/重放交 R23。
- 真实 DeepSeek 调用在本沙箱仍 `NOT_RUN`（Python TLS），但**生成图不调用模型**，不影响 M23。
- 无阻塞。
