## 2. Goal 与判定

**Goal：** 建立**结构化模块变更请求**机制：消费者提出所需能力/契约修改，Coordinator 核验所有权/依赖/DAG/预算后，
把变更任务分配给**真正负责该模块**的 Agent；模块间只传**经批准的公共接口**。

**结论：** 协议 `request_id/requester_module/target_module/capability_id/required_contract/change_reason/
acceptance_ids/status/spec_ref` 落地；业务范围变更**须用户确认**；自循环/循环依赖/预算不足/反复提议一律阻塞；
同 id 重放幂等；破坏性变更有**受影响消费者分析**；协调器**无模型参与**、不越权。

## 5. 关键设计

- **非监督者、非路由模型**：纯确定性 Python；`ModuleCoordinator` 不引用模型网关/客户端。
- **业务 vs 技术**：`CAPABILITY_REQUEST`（技术）→ 待派发；`SCOPE_CHANGE`（新业务范围/权限/Profile）→
  `PENDING_USER`，必须 DeepSeek 用户确认并提供**新冻结 spec 引用**；拒绝 → `REJECTED`（草稿保留，不擅自继续）。
- **不越权**：`assign` 只派发给**目标模块**（模块 A 不得写 B）；写权限仍由 F01/F04 强制。
- **阻塞项**：自循环（requester==target）、未知模块、**循环依赖**（目标已传递依赖请求者）、预算不足、
  反复提议超上限（转人工）。
- **幂等**：同 `request_id` 重放返回既有结果，不新增。
- **破坏性变更**：`breaking_consumers(capability_id)` 列出依赖提供者的模块，供升级前核验/迁移（禁止静默覆盖）。
