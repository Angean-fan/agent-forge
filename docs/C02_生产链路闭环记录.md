## 4. 修复的接线断点（S2 实质）

**现象：** 经 C01 生产路由注入后，`repair_node` 走**真实**受限引擎（`LedgerChatModel`）时，首次内部模型请求即失败 `VALIDATION_ERROR`。

**根因：** `LedgerChatModel._reserve` → `model_gateway.reserve` → `_require_task_context(db, run_id, "repair:verify")` 要求该任务行**已存在**；而 `repair_node` 原实现只在 `run_repair_loop` **之后**（`generation_graph.py:405`）才 `record_task_once(... "repair:verify")`。R18 的既有测试用不落账本的脚本引擎（`SimpleNamespace`）注入，故从未触发该校验 → 生产路径的真实账本才暴露此断点（正是 S2「生产未接线」的表现）。

**修复：** 在 `run_repair_loop` 之前、当且仅当 `classify_repair_failure(state["verification"], state["acceptance"]) == CODE` 时预登记 `repair:verify`（`status="RUNNING"`）；循环结束后的既有更新逻辑不变（找到该行并写 `attempt`/`status`）。基础设施故障（分类 ≠ CODE）不预登记，避免悬空任务。

**兼容性：** `repair_node` 对外行为不变；仅新增一次幂等的任务行写入（`record_task_once`）。
